# REALESTATE — MASTER PLATFORM AUDIT & DELIVERY PROMPT

Act as the principal engineering, product, UX, 3D, QA, security and release agent for this repository.

## Mission
Turn REALESTATE into a coherent, production-oriented real-estate showroom platform. Do not optimize isolated screens while the platform circuit is incomplete. Preserve the renderer-agnostic architecture and make the whole system behave as if a real developer were using it.

## Product contract
REALESTATE has four surfaces:
- `/studio`: private REALESTATE operator workspace. Create projects, ingest files, validate AI proposals, generate, approve and publish.
- `/cliente/:slug`: private client portal. Edit permitted commercial data such as price/availability, inspect metrics, request service and access the published experience.
- `/proyecto/:slug`: public cinematic showroom.
- `/embed/:slug`: public read-only embeddable showroom.

The canonical flow is:
`create → ingest → normalize → validate → generate → review → approve → publish → operate → analytics`.

The public showroom must consume the published project manifest, not a parallel hardcoded dataset. Interior apartment exploration is a primary sales experience: exterior → building → floor → unit → interior → room → CTA.

## Non-negotiable architecture
1. One canonical project contract and one canonical inventory source.
2. Frontend is a consumer of platform state; localStorage may be a fallback only, never the authoritative production source.
3. Renderer is replaceable. Current tiers: Three standard/premium and future Unreal/Pixel Streaming ultra.
4. Tenant boundaries must be enforced server-side. Never trust `companyId` supplied by an untrusted client.
5. Public routes expose only published, public-safe project data.
6. Client users may not modify engine/global settings, other tenants, or structural data outside their role.
7. Human approval remains required before publication.
8. Analytics must use stable event names and feed the client portal from persisted events.
9. Remove obsolete duplicate implementations only after proving they have no active consumers.
10. Do not add dependencies unless necessary and justified.

## Audit instructions
Before changing code:
- inspect package scripts and architecture;
- inspect route wiring and all platform modules;
- search for duplicate implementations, hardcoded project data, fake metrics, dead imports, unreachable routes, stale TODO/FIXME, and localStorage used as authoritative persistence;
- trace every public/client/studio flow end to end;
- identify build/runtime/test risks.

## Code quality rules
- Prefer small cohesive modules.
- Avoid duplicated business rules between frontend and backend.
- Keep data normalization explicit.
- Keep API errors actionable.
- Preserve backwards compatibility when practical; otherwise migrate cleanly and delete dead code.
- No fake success states for production paths.
- No silent catch blocks around critical persistence operations; surface a fallback state and error reason.
- Every new API mutation gets validation and a test.
- Every critical public/client route gets an integration test.
- Build must pass before release.

## Definition of done for this pass
A reviewer should be able to follow a project from Studio to published showroom and then to Client Portal without manually editing localStorage or code. The showroom and portal must read the same project/inventory state. Analytics generated by showroom interactions must become visible to the client portal. A failed backend should produce an explicit degraded state, not falsely claim that data was published.

## Cleanup policy
Delete code only when it is provably unused, superseded, or contradictory. Before deleting, search all imports/references. Prefer consolidating duplicate helpers into the canonical platform modules. Never delete working renderer fallbacks solely because a future renderer is planned.

## Verification checklist
Run:
- `npm test` or the repository's API test script;
- `npm run build`;
- targeted lifecycle/inventory/manifest/analytics tests;
- inspect deployment/build status;
- verify `/studio`, `/cliente/:slug`, `/proyecto/:slug`, `/embed/:slug`, and `/proyecto/:slug/interior`.

Report only verified results. Clearly separate completed, degraded/fallback, and remaining work.

## Product owner constraint
Do not stop at architecture diagrams. Implement the highest-value missing pieces, keep the codebase coherent, and leave the repository in a runnable state. The final goal is a commercially usable platform with cinematic visualization layered on top—not a collection of disconnected demos.
